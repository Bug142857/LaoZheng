# 老郑分享 PC 端 P0–P3 优化审查与运行时实测报告

- 审查对象：老郑分享 PC 端（Electron + React + TypeScript）
- 审查时工作区版本：`0.208.0`
- 审查时运行环境：Windows、Electron `33.4.11`、Chrome `130.0.6723.191`
- 审查方式：静态代码审查 + 生产构建真实客户端 CDP 运行时实测
- 报告日期：2026-11-19
- 说明：本报告保留 2026-11-19 的审查原文与实测数据；实施状态见第 11 节（2026-11-20 更新），所有运行时测试痕迹均已清理。

## 1. 结论摘要

当前最值得优先处理的不是界面细节，而是以下四条主线：

1. **稳定性与数据安全**：React 渲染异常会直接导致整个应用白屏；整体导入和云恢复覆盖本机数据前不会自动留下可回滚快照。
2. **性能与资源占用**：播放进度每约 8 秒触发一次整份 `data.json` 重写；访问过的模块持续驻留，浏览 21 个模块后进程组内存由 403.4 MB 增至 1,043.6 MB。
3. **核心使用体验**：下载没有全局并发限制，播放器缺少倍速和画中画，音乐没有音量控制，窗口尺寸不记忆，主页没有“继续观看”。
4. **工程维护**：巨型文件、单一大包、缺少解析器测试和日常 CI 门槛，会持续增加后续修改与发版风险。

建议总顺序：

> **错误边界与覆盖前快照 → 播放进度拆独立存储 → 模块卸载策略 → 下载全局并发与速度显示 → 窗口记忆与音乐音量 → 图片缓存淘汰 → CI、解析器测试与代码拆分**

Electron 升级和隐藏窗口 `sandbox` 收紧建议单独安排一轮完整回归，不与大规模功能修改混在一起。

## 2. 实测方法与判定口径

### 2.1 运行时方法

- 使用生产构建启动真实 Electron 客户端，通过 CDP 检查 DOM、JS 堆、进程内存、网络目标、播放进度、下载行为、窗口尺寸和快捷键。
- P0 破坏性测试使用独立临时 `userData`，真实用户数据不参与测试。
- 图片缓存测试使用本地秒级小图，不下载公网大文件。
- 构建与包体数据来自实际 `typecheck / build` 输出。
- 静态审查负责确认代码路径和配置；运行时实测负责验证行为。二者在表中分别标明。

### 2.2 状态说明

- **实测确认**：已在真实客户端复现并取得数据。
- **静态确认**：代码路径或配置明确，但本轮未做针对性运行时复现。
- **已有保护**：当前已经有效，不需要重复建设，但应纳入回归测试。
- **建议项**：原始建议；当前实施状态见第 11 节（2026-11-20）。

## 3. P0：稳定性、数据安全与安全基线

### P0-1 React 渲染异常会导致整页白屏

**状态：实测确认，优先修复。**

实测向 React 状态更新注入一次渲染异常：

- 根节点子元素数量：`1 → 0`
- 侧栏：消失
- 页面正文：空白
- 刷新后：根节点恢复为 `1`，UI 恢复正常

普通异步 JS 异常则不会直接白屏：注入后侧栏仍在、preload API 可用、根节点保持为 `1`。因此不能把“普通报错没白屏”误认为已经具备渲染错误兜底。

当前 [App.tsx](../src/App.tsx#L500-L515) 只处理数据替换和保存失败提示，`src` 中未发现 `ErrorBoundary`、`componentDidCatch` 或 `getDerivedStateFromError`。

**建议：**

- 在数据层和模块容器外增加 React 错误边界。
- 错误页至少提供“重新加载”和“打开数据目录”。
- 单个模块异常时尽量只卸载该模块，避免整个应用不可用。
- 记录模块名和错误堆栈，但不要写入账号、Cookie 等敏感信息。

### P0-2 整体导入和云恢复前没有自动本地快照

**状态：覆盖落盘链路实测确认，云恢复代码路径静态确认。**

整体导入经 [SettingsPage.tsx](../src/pages/SettingsPage.tsx#L218-L247) 进入 `replaceData`；云恢复经同文件 [confirmSyncImport](../src/pages/SettingsPage.tsx#L379-L389) 进入同一替换入口。

按两条链路最终共用的 `saveData` 落盘方式实测：

- 新标记成功持久化。
- 覆盖后自动生成的 `data.json` 历史备份数：`0`。
- 临时 `.tmp` 文件残留数：`0`。

现有确认弹窗能防止误触，但**确认覆盖不等于可以回滚**。弹窗也只是建议用户先手动导出或上传云端。

**建议：**

- 整体导入、云恢复确认后，在覆盖前自动生成带时间戳的本地快照。
- 保留最近若干份，并提供本地恢复入口。
- 快照应放在固定、可发现的数据目录中，并设置数量或容量上限。
- 对快照创建失败要中止覆盖并明确提示，不能静默继续。

### P0-3 图片缓存正常运行时无自动淘汰

**状态：实测确认。**

运行时连续加载 12 张不同的秒级小图：

- 图片加载成功：`12 / 12`
- 图片缓存文件：`0 → 12`
- 运行期间未观察到自动淘汰
- 手动清理成功，释放缓存总量：`8,226,336` 字节
- 清理后图片缓存文件：`0`

[imageCache.ts](../electron/imageCache.ts#L192-L267) 只有命中读取、网络回源、落盘和坏图删除，没有容量上限、LRU 或时间淘汰；[main.ts](../electron/main.ts#L1008-L1033) 的手动清理有效。

**建议：**

- 增加容量上限和 LRU 淘汰，避免长期使用后无限增长。
- 淘汰时避免删除正在读取的文件。
- 保留现有手动清理，并显示图片缓存、接口缓存分别占用多少空间。
- 清理和淘汰只影响缓存，不得影响收藏、清单、阅读进度和登录态。

### P0-4 Electron 版本偏旧，通用隐藏取页窗口未启用 sandbox

**状态：运行时版本确认，窗口配置静态确认。**

运行时 UA：

- Electron：`33.4.11`
- Chrome：`130.0.6723.191`
- 应用版本：`0.208.0`

主窗口安全配置有效，见 [main.ts](../electron/main.ts#L375-L393)：

- `contextIsolation: true`
- `nodeIntegration: false`
- `sandbox: true`
- 渲染层实测 `process === undefined`、`require === undefined`
- preload API 正常可用

但通用隐藏取页窗口 [browserPage.ts](../electron/browserPage.ts#L26-L30) 仍为 `sandbox: false`。

**建议：**

- 评估通用取页窗口改回 `sandbox: true`，该窗口没有 preload 和 Node 依赖，具备收紧条件。
- Electron 升级单独进行，重点回归 HLS、下载、隐藏窗口取页、扫码登录、本地媒体和安装更新链路。
- 本次未做漏洞利用测试，不将“版本偏旧”表述为已复现漏洞。

### P0 已有且实测有效的保护

1. **损坏数据会保留副本**：人为破坏隔离环境的 `data.json` 后重启，生成 1 个 `.broken-*` 文件，内容与原损坏文件逐字一致，应用成功启动，数据结构恢复合法。实现见 [store.ts](../electron/store.ts#L16-L31)。
2. **正常保存采用原子替换**：先写临时文件再 `rename`，并有保存序号和重试机制，见 [store.ts](../electron/store.ts#L35-L120)。
3. **主进程异常有日志和提示**：`uncaughtException` 会写 `crash.log`、显示错误框并退出，见 [main.ts](../electron/main.ts#L4391-L4415)。
4. **主窗口渲染层无直接 Node 权限**：运行时和配置均确认有效。

> 注意：损坏恢复会保留原始损坏文件，但应用恢复后的数据不等于用户此前的完整历史数据，因此仍需要 P0-2 的定期 / 覆盖前快照。

## 4. P1：性能与资源占用

### P1-1 播放进度造成整份数据写放大

**状态：实测确认，收益最高。**

当前链路：

- [VideoPlayer.tsx](../src/components/VideoPlayer.tsx) 在播放进度与上次保存值相差至少 8 秒时更新 `readProgress`。
- [DataContext.tsx](../src/state/DataContext.tsx#L1-L120) 的 `update()` 更新整份 React 数据，并在 350ms 防抖后调用 `saveData`。
- 每次保存都会序列化并重写整份 `data.json`。

实测：

- 播放期间在约第 `2s / 10s / 18s` 观察到三次文件变更。
- 播放时每次重写文件约 `1,262,096` 字节。
- 当前真实 `data.json` 基线：`1,262,020` 字节。
- 数据 JSON 字符长度：`819,055`。
- `saveData` 实测约 `25ms`，`loadData` 约 `23ms`。

**建议：**

- 播放进度改为主进程独立文件或独立键值存储，渲染层只提交 `key + seconds`。
- 内存中立即更新，磁盘按时间窗口批量写入；暂停、退出和切集时立即刷新。
- 独立存储仍必须纳入整体导入导出和云同步，不能形成新的数据孤岛。
- 保留现有“续播”行为，避免为了降写入而丢失最后进度。

### P1-2 访问过的模块全部常驻，DOM 和内存持续上涨

**状态：实测确认。**

[App.tsx](../src/App.tsx#L493-L520) 的 `visited` 只增不减，访问过的模块通过 `display:none` 保留在 DOM 中。

浏览 21 个模块后的实测：

| 指标 | 初始 | 浏览 21 个模块后 | 回到主页后 |
|---|---:|---:|---:|
| DOM 节点 | 596 | 20,823 | 20,556 |
| JS 堆 | 8.2 MB | 34.3 MB | 27.4 MB |
| 进程组内存 | 403.4 MB | 1,043.6 MB | 未完全回落 |

**建议：**

- 为非活动模块制定卸载或有限 KeepAlive 策略，不再无限保留。
- 播放器、下载页、搜索状态、滚动位置分别评估，不做“一刀切”卸载。
- 列表数据优先使用已有磁盘 / 内存缓存恢复，滚动位置单独保存。
- 修改后重复同一组 21 模块浏览测试，对比 DOM、JS 堆和进程组内存。

### P1-3 下载任务没有全局并发上限

**状态：实测确认。**

[downloads.ts](../electron/downloads.ts) 的 `addDownload` 构造任务后直接 `startTask`，没有全局队列上限；HLS 单任务已有 5 并发切片，但多任务之间仍可同时运行。

实测两个本地下载任务：

- 启动后约 `2.2s`，两个任务同时到达 `28%`。
- 两者均已下载 `1,245,184` 字节。

**建议：**

- 增加全局并发上限和等待队列，必要时再按站点限制并发。
- HLS 的切片并发与任务并发分开计算。
- 暂停、继续、取消、应用退出和失败重试都必须保持队列状态一致。
- 与 P2 的下载速度、ETA 和完成通知一起实施，减少重复改动。

### P1-4 长列表没有统一虚拟滚动

**状态：静态确认，本轮未做大数据量基准测试。**

漫画、套图、搜索结果、收藏和清单等列表继续增长时，会直接增加 DOM 和 React 节点；P1-2 的常驻策略会进一步放大这一问题。

**建议：**

- 优先给真实可能达到数百至数千项的列表增加虚拟化或窗口化渲染。
- 先选一个长列表做基准，不必一次性重写所有页面。
- 虚拟化必须保留图片懒加载、批量选择、滚动恢复和键盘操作。

## 5. P2：使用体验

### P2-1 影视播放器缺少倍速、画中画，原生全屏会丢失清晰度控件

**状态：实测确认。**

[VideoPlayer.tsx](../src/components/VideoPlayer.tsx) 使用原生 `<video controls autoPlay playsInline>`，清晰度下拉是 `<video>` 的兄弟节点。

实测：

- 全屏时 `fullscreenElement` 是 `<video>`，不是整个播放器容器。
- 因此自建清晰度控件不会随视频进入全屏。
- 未提供应用内倍速和画中画入口。
- 原生控件聚焦时，空格暂停 / 播放和方向键跳转有效，不能误报为“完全不支持键盘”。

**建议：**

- 参考 [BiliPlayer.tsx](../src/components/BiliPlayer.tsx) 的 `.player-stage`，对整个播放器容器调用 Fullscreen API。
- 增加倍速、画中画，并保证清晰度、弹幕 / 工具层在全屏中仍可使用。
- 快捷键在输入框、下拉框和原生控件聚焦时避免冲突。

### P2-2 音乐没有音量 / 静音控制，播放队列只存内存

**状态：实测与静态共同确认。**

- 底部音乐条只检测到 1 个 `range`，用途为播放进度。
- [MusicPlayer.tsx](../src/components/MusicPlayer.tsx) 的 `new Audio()` 未设置音量，没有音量 / 静音控件。
- 播放队列只保存在内存中。

**建议：**

- 增加音量滑块和静音按钮，记住上次音量。
- 明确主页播放器与音乐模块播放器的队列和状态同步口径。
- 若增加持久化队列或新设置字段，必须同步进入导入导出和云同步。

### P2-3 主页缺少“继续观看”

**状态：实测确认。**

主页实测有 17 个分组，但没有“继续观看”。影视播放已经写入 `vodEp|<source>|<vod_id>` 和 `video/<hash>` 等进度，具备做续播入口的数据基础。

**建议：**

- 在主页增加最近观看分区，显示标题、片源、集数和最近播放时间。
- 点击后尽量直接续播；失效条目允许单独移除。
- 最近观看时间和入口展示所需字段必须进入备份和云同步。

### P2-4 窗口尺寸和位置不记忆

**状态：实测确认。**

将窗口调整为 `1000 × 700` 后重启，恢复为 `1280 × 820`。当前 [main.ts](../electron/main.ts#L375-L393) 固定创建尺寸，没有 bounds 持久化。

**建议：**

- 正常关闭或尺寸 / 位置变化防抖保存窗口 bounds。
- 重启时校验显示器区域，避免拔掉显示器后窗口落到屏幕外。
- 最大化状态单独保存，不要直接恢复成过大的普通窗口。

### P2-5 缺少明确的全局 / 页面快捷键

**状态：实测确认。**

按下 `Ctrl+F` 前后，`document.activeElement` 均为 `BODY`，没有进入页面搜索框。

**建议：**

- 根据当前页面定义 `Ctrl+F`：聚焦模块搜索或收藏过滤，不重复弹全局搜索。
- 播放器快捷键与输入框、文本选择、原生视频控件保持兼容。
- 快捷键数量保持精简，并在界面中提供可发现的提示。

### P2-6 下载浮条缺少速度和 ETA，完成反馈可加强

**状态：实测与静态共同确认。**

[DownloadCenter.tsx](../src/components/DownloadCenter.tsx#L100-L169) 浮动条主要显示百分比和字节数，没有实时速度与预计剩余时间。

**建议：**

- 显示平滑后的实时速度、ETA 和等待队列状态。
- 下载完成、失败时提供系统通知；仅用户主动开始或应用处于后台时通知，避免打扰。
- 与 P1-3 的全局下载队列统一设计和验证。

### P2-7 启动时后台登录检查影响离线体验

**状态：实测确认。**

启动约 14 秒后出现 `z-lib.sk` 隐藏页面；离线环境中观察到多次 `ERR_CONNECTION_TIMED_OUT`。主进程启动时还会调用哔咔、Komiic、无忧和 Z-Library 的登录检查。

**建议：**

- 将非关键登录检查改为按需触发或延迟空闲执行。
- 离线时快速失败并指数退避，不反复创建窗口和请求。
- 保留已有会话恢复，不影响用户真正进入模块时的自动登录。

### P2-8 小说阅读器排版自定义不足

**状态：静态确认，本轮未做阅读时长主观评测。**

**建议：**

- 提供字号、行距、阅读背景和页面宽度设置。
- 设置按本机持久化；若进入通用设置数据，则同步纳入导入导出和云同步。
- 保持章节进度和滚动恢复不受影响。

### P2-9 壁纸入口仍可更直接

**状态：修正后保留为低优先级建议。**

下载管理已经支持“设为壁纸”，见 [DownloadsPage.tsx](../src/pages/DownloadsPage.tsx#L254-L255) 和同文件第 643、697 行附近按钮。

可选优化是让用户在壁纸模块详情页直接设置，不必先进入下载管理；这不是“壁纸只能下载”的功能缺失。

## 6. P3：工程维护与交付质量

### P3-1 巨型文件职责集中

**状态：静态确认。**

重点关注：

- `SourceSettings.tsx`
- `main.ts`
- `novel.ts`
- `downloads.ts`
- `trainers.ts`

这些文件当前需要分段阅读，数据来源、IPC、业务逻辑和 UI 职责集中，修改时容易牵连其他模块。

**建议：**

- 按真实变更方向拆分，不为追求文件数量而机械拆分。
- `main.ts` 优先拆 IPC 注册、缓存管理、窗口生命周期和启动流程。
- 页面优先拆数据源配置卡片、通用操作和类型定义。
- 每次拆分保持行为不变，并配合 typecheck、构建和针对性运行时回归。

### P3-2 渲染层单包过大，缺少按页代码分割

**状态：构建实测确认。**

实测数据：

- `typecheck`：约 `10.6s`
- 完整构建：约 `20s`
- renderer 单 chunk：约 `3,015 KB`
- main：约 `1,793 KB`
- CSS：约 `87 KB`

**建议：**

- 按路由 / 大模块做 `lazy` 和动态导入，将 hls.js、mpegts.js 等重依赖留在使用它们的 chunk。
- 先处理首屏用不到的大模块，再评估 vendor 拆分。
- 与 P1-2 的模块卸载策略协同，避免懒加载和 KeepAlive 相互抵消。

### P3-3 站点解析器缺少自动化测试

**状态：静态确认。**

`src` 和 `electron` 未发现测试 / spec 文件，`package.json` 也没有 `test` 脚本。影视、漫画、小说、资讯等模块高度依赖站点 HTML / JSON 结构，站点微调后容易静默失效。

**建议：**

- 优先给纯解析函数增加小型固定样例测试，不在测试中访问真实站点。
- 覆盖正常页、空列表、字段缺失、分页末端和站点错误页。
- 对图片解密、禁漫还原、进度键、备份 normalize 等纯逻辑优先补回归测试。
- 测试样例去账号、去 Cookie、去私人数据。

### P3-4 CI 只有发版构建，没有日常质量门槛

**状态：静态确认，修正“没有 CI”的旧结论。**

[build-release.yml](../.github/workflows/build-release.yml) 当前仅由：

- `push.tags: v*`
- `workflow_dispatch`

触发。它能构建安装包并上传 Release，但普通 PR / push 不会自动执行 typecheck 和 build。

**建议：**

- 增加 PR / 主分支 push 的轻量质量任务：安装依赖、typecheck、build、解析器测试。
- 发版 workflow 继续负责安装包和 Release，不重复上传日常构建产物。
- PR 环境不能使用账号种子时沿用空种子构建，确保不泄露 `.secrets`。

## 7. 已修正的初审结论

以下三项以运行时实测和复查结果为准：

1. **壁纸不是只能下载**：下载管理已有“设为壁纸”按钮和 `setWallpaper` IPC。
2. **项目不是完全没有 CI**：已有 GitHub Actions 发版构建，但只由 tag / 手动触发，缺少 PR 和日常 push 质量门槛。
3. **原生视频控件不是完全不支持快捷键**：控件聚焦时空格和方向键有效；仍缺应用级统一快捷键、倍速和画中画。

另有一项测量未纳入结论：收藏、清单、下载属于 route 页，不在 `[data-page-slot]` 内，因此当时针对收藏页取得的 `els:0 / slot:null` 不作为常驻模块证据。
